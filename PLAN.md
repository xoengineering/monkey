# Monkey — Build Plan

Local-only chat app for Apple's on-device Foundation Models. macOS / iOS / iPadOS. Swift + SwiftUI. Open source, free on the App Store, no IAP.

Sections marked **[verify]** are assumptions Claude Code should confirm against current Apple docs (Xcode 27 SDK) before implementing. Everything else is either user-specified or stable knowledge.

---

## 1. Hard constraints

- Platforms: macOS 27, iOS 27, iPadOS 27. Nothing lower. No visionOS/watchOS/tvOS.
- Swift 6 language mode, strict concurrency. SwiftUI only. No UIKit/AppKit except where SwiftUI has no equivalent (wrap, don't leak).
- No Electron, no web views, no cross-platform layers.
- Network posture (a technical design rule, not a marketing slogan; the marketing will explain exactly what is opt-in): the app itself opens no sockets. Do not add the `com.apple.security.network.client` entitlement on macOS. No `URLSession`, no analytics, no crash reporters. Model inference is on-device only. The one opt-in exception is iCloud Drive sync of the conversation folders (§3a), which is off by default and handled by the system's iCloud daemon, not by the app's process. With it off, the app is fully air-gapped once installed.
- App Sandbox on. Files stay inside the app container, or in the app's iCloud ubiquity container when the user opts in.
- Model: `FoundationModels` framework, `SystemLanguageModel` **on-device only**. iOS 27 adds Private Cloud Compute and third-party `LanguageModel` conformers — do not use any of them. Only the on-device system model. **[verified]** against the installed macOS 27 SDK: `SystemLanguageModel` and `PrivateCloudComputeLanguageModel` are separate, unrelated classes with no mode switch between them. Hard-pinning on-device means constructing sessions only via `SystemLanguageModel.default` (e.g. `LanguageModelSession(model: SystemLanguageModel.default, ...)`) and never referencing `PrivateCloudComputeLanguageModel` anywhere in the codebase.
- Single user. No accounts, no sync.
- Open source, MIT license. Same repo ships to App Store. Free, no IAP, no limits.

- One multiplatform app target, not three. `#if os(macOS)` only where unavoidable.
- Dependencies: Yams (jpsim/Yams) in Core for YAML; Textual (gonzalezreal/textual, ≥0.5.0) in UI for markdown rendering; swift-argument-parser in the CLI target. Pin all to tagged releases. No hand-rolled parsers or renderers.
- Bundle ID / team / product ID: leave as placeholders; user fills in. In practice: `PRODUCT_BUNDLE_IDENTIFIER` comes from `App/Local.xcconfig` (gitignored, created from `Local.xcconfig.example` by `script/bootstrap`). `DEVELOPMENT_TEAM` is deliberately _not_ in that xcconfig, and not in `project.yml` `settings:` either — **[verified]** by direct test: putting `DEVELOPMENT_TEAM` in a `configFiles:`-referenced xcconfig and running `xcodegen generate` wrote `DevelopmentTeam = <id>;` into `TargetAttributes` in the shared, tracked `project.pbxproj`, regardless of the xcconfig file itself being gitignored — XcodeGen resolves the value at generate time and bakes it into the tracked file, and `script/bootstrap` runs `xcodegen generate` on every build, so this would leak a real team ID on every regeneration. Team ID instead lives in a repo-root `.env` (gitignored, created from tracked `.env.example` by `script/bootstrap`) that `script/run` sources as a plain shell script and passes to `xcodebuild` only as a trailing command-line override — this never touches `project.yml`/xcconfig/xcodegen, so it can't leak into `project.pbxproj`. Verified: `codesign -dv` on the built app shows `TeamIdentifier=<id>` matching `.env`, and `git status` shows zero tracked-file changes after the build. Xcode's own Signing & Capabilities tab (stored in gitignored `xcuserdata`) also still works as a per-user alternative.

## 3. On-disk format

Root: `~/Library/Application Support/<bundle-id>/Conversations/` (inside the sandbox container on all platforms; use `FileManager.url(for: .applicationSupportDirectory, in: .userDomainMask, ...)`).

```txt
Conversations/
  2026-09-15T14-32-08.123Z-k7x2q9/       # same <timestamp>-<key> scheme as messages
    conversation.yaml
    2026-09-15T14-32-08.123Z-k7x2q9.md
    2026-09-15T14-32-41.507Z-m3pd1w.md
    ...
```

### `conversation.yaml`

```yaml
id: 2026-09-15T14-32-08.123Z-k7x2q9 # equals the folder name
title: Untitled
created_at: 2026-09-15T14:32:08.123Z
updated_at: 2026-09-15T14:32:41.507Z # any metadata write bumps this (rename, instructions, messages)
last_message_at: 2026-09-15T14:32:41.507Z # newest message's created_at; absent until the first message
instructions: "" # optional instructions for the model session; blank by default
message_count: 2 # cache; source of truth is the directory listing
```

### Message file: `<timestamp>-<key>.md`

- Timestamp: UTC, ISO-8601, colons replaced with `-` for filesystem safety, millisecond precision: `2026-09-15T14-32-08.123Z`.
- Key: 6-char base32/base36 random string. Purpose: two writes in the same millisecond never collide. Lexical sort by filename == chronological order.
- Frontmatter: flat YAML between `---` fences. Body: raw markdown, exactly what the user typed or the model produced.

```markdown
---
id: k7x2q9
role: user # user | assistant
created_at: 2026-09-15T14:32:08.123Z
status: complete # complete | streaming | cancelled | failed
model: system-on-device # opaque string; whatever the framework reports
in_reply_to: "" # id of the message this answers (assistant msgs)
tokens_prompt: 0 # optional; only if the SDK exposes counts
tokens_output: 0
error: "" # populated when status == failed
---

The actual markdown body.
```

### Rules

- Write atomically: write to a temp file in the same directory, then `replaceItemAt`. Never partially-written message files on disk.
- Streaming assistant replies: create the file with `status: streaming` and an empty body on first token; rewrite body at a throttled cadence (e.g. every 250 ms) while streaming; final write sets `status: complete`. On app kill mid-stream, the file exists with `status: streaming` — on next load, mark it `cancelled` (don't delete; the partial text is still useful).
- Deleting a conversation = delete the directory. Deleting a message = delete the file and update `conversation.yaml`.
- The directory listing is the index. `conversation.yaml.message_count` is a hint for UI badges, never trusted for pagination.
- Files must be plain enough to open in any editor. This is the export format too — "export" is just "reveal in Finder / share the folder".

## 3a. Storage location and opt-in iCloud sync

`ConversationStore` is initialized with a root URL. There are exactly two roots; the user picks one in Settings.

- **On device (default).** The **app group** container, so the app and the bundled CLI (§6) share it: macOS `~/Library/Group Containers/<team-id>.<group>/Conversations/`; iOS/iPadOS the equivalent group container. Nothing leaves the device. Resolved by `AppGroupStorage.conversationsRootURL()` in `MonkeyCore` (§5).
- **iCloud Drive (opt-in).** `FileManager.url(forUbiquityContainerIdentifier:)` + `Documents/Conversations/`. Requires the iCloud entitlement (CloudDocuments service, one container ID) and an iCloud-capable provisioning profile. Does not require the network entitlement — the iCloud daemon moves bytes, not the app. **[verified]** via throwaway spike `spike/2-icloud-documents-sync` (not merged): a sandboxed macOS app and a sandboxed iOS app, both with only `com.apple.developer.icloud-services=[CloudDocuments]` + `com.apple.developer.icloud-container-identifiers=[iCloud.<bundle-id>]` — no network entitlement, no `aps-environment` — shared one iCloud container. The Mac wrote a timestamped file; a physical iPhone (separate bundle ID, same container ID) read back the exact same content with no trust prompt and no app-level networking, confirming real cross-device iCloud Drive sync end to end.

Both roots are resolved by `ConversationsRootResolver.resolve(location:fileManager:)` in `MonkeyCore`, given a `StorageLocation` (`.onDevice` / `.iCloud`). Returns `nil` for `.iCloud` when no ubiquity container is available (signed out, disabled, entitlement missing) — callers fall back to `.onDevice`. The choice itself is persisted by `StorageLocationPreference` in the app group's shared `UserDefaults` suite, so the CLI reads the same choice the app's Settings made (§5).

Switching: implemented as `ConversationMigrator` in `MonkeyCore` — moves each conversation folder with `setUbiquitous(true, itemAt:destinationURL:)` (on-device → iCloud) or `setUbiquitous(false, ...)` (the reverse), skipping folders already present at the destination so an interrupted migration is resumable by just calling `migrate` again. Tested (4 tests) with an injectable `Mover` closure standing in for `setUbiquitous` (which needs a real ubiquity container to run for real) — the resumability/skip logic and progress reporting are exercised directly; the real `setUbiquitous` call itself is unverified this session (needs a real device/iCloud account). UI wiring (Settings picker, per-conversation progress, "sending disabled during migration") is not yet built — see the gap note at the end of this section.

Cloud-mode behavior in `ConversationStore` — **implemented, not gated on a mode flag**: since `NSFileCoordinator` works correctly for purely local files too (coordination is a general local mechanism, not iCloud-specific), all reads/writes go through it unconditionally, and `ConversationStore.startPresenting()`/`stopPresenting()` register/unregister an `NSFilePresenter` for the root. This means it's testable without any real iCloud container:

- All reads/writes through `NSFileCoordinator` (`coordinatedRead`/`coordinatedWrite`/`coordinatedRemove`). **[verified]**: full existing test suite (68 Core+UI tests) stayed green after the retrofit, confirming no on-device-mode regression.
- `NSFilePresenter` registered via `startPresenting()`; a `ConversationsRootFilePresenter` (a plain `NSObject` subclass, since actors can't subclass `NSObject`) forwards `presentedSubitemDidChange`/`accommodatePresentedSubitemDeletion` into the actor, which evicts the affected message from the in-memory cache. **[verified]** by a real test (`externalWriteInvalidatesTheCachedMessage`): a *second*, independent `NSFileCoordinator` writes directly to an already-cached message file (simulating another process/device), and the store's next `loadMessage` call returns the new content — proving the presenter plumbing genuinely fires, entirely locally, no iCloud needed. Confirmed stable across repeated runs (~1.1s each, since the callback is asynchronous).
- Streaming rewrites are already throttled (≥250 ms) by `ModelSession` — unchanged, predates this phase.
- **Not implemented this session** (the two most iCloud-infrastructure-dependent pieces, genuinely impossible to verify without a live multi-device iCloud account): `NSMetadataQuery`-driven discovery of not-yet-downloaded remote items + `startDownloadingUbiquitousItem` + placeholder rows; and `NSFileVersion`-based `conversation.yaml` conflict resolution. Both are still designed as originally planned (see below); implementing them blind, with zero ability to exercise real conflict/download scenarios, seemed like a worse trade than documenting the gap plainly. Whoever picks this up with real device access should treat these two as the remaining Phase 6 core-logic work, alongside the Settings UI (below).
- The design invariant that makes all this cheap: one immutable-ish file per message, timestamp+key names, directory listing as index. Keep it.

**Settings UI implemented and [verified] live** (not just built — actually clicked through in the running app, screenshotted): a new `AppEnvironment` (`@MainActor @Observable`, `Sources/MonkeyUI/AppEnvironment.swift`) owns the current `ConversationStore`/`ConversationListViewModel` and `switchStorageLocation(to:)`, which runs the migration and, on success, adopts a new store (replacing a store's root isn't possible in place — `ConversationStore.rootURL` is fixed at init). `MonkeyRootView` now owns `AppEnvironment` instead of a raw store, keying the sidebar's `.task` on `environment.generation` so it re-fetches after a storage switch. `SettingsView` gained a Storage section: a Location picker (On This Device / iCloud Drive), migration progress, the resolved data folder path, and (macOS only, via a narrowly-scoped `NSWorkspace` import — no SwiftUI equivalent exists) a "Show Data Folder in Finder" button. **[verified]** two real runs in the built app: (1) the Storage section renders correctly with the real app-group path shown and "On This Device" selected — this initially appeared to be *missing entirely* because the sheet's original `minHeight: 320` clipped it with no visible scroll affordance; fixed by growing the frame to `420×480`; (2) clicking "iCloud Drive" (with no iCloud entitlement added yet, see below) correctly hit the `nil`-ubiquity-container fallback and surfaced "Something Went Wrong: iCloud Drive isn't available right now" via the existing alert — exactly the designed graceful-failure path, no crash. This also incidentally fixed the Phase 4 sidebar-staleness gap: `ConversationDetailViewModel` now takes an `onConversationUpdated` callback, invoked after every send, which `MonkeyRootView` wires to `environment.listViewModel.refresh()`.

**iCloud entitlements attempted and reverted — a real, documented finding, not a code bug.** Added `com.apple.developer.icloud-container-identifiers` + `com.apple.developer.icloud-services` + `com.apple.developer.ubiquity-container-identifiers` to both `Monkey.entitlements` and `MonkeyCLI.entitlements` and tried to build with `-allowProvisioningUpdates` (already in `script/run`). Result: `error: Provisioning profile ... doesn't match the entitlements file's values for the com.apple.developer.ubiquity-container-identifiers and com.apple.developer.icloud-container-identifiers entitlements`, even under the same Developer ID Application team that automatic-signs the app group successfully today. Tried the other available identity (a personal Apple Development team) too — that one has no active Xcode Accounts session (`error: No Account for Team "<team id>"`), so it can't drive `-allowProvisioningUpdates` at all. This matches a well-known real limitation: `-allowProvisioningUpdates` can add most App ID capabilities headlessly, but creating a brand-new iCloud container appears to need one interactive pass through Xcode's Signing & Capabilities tab (click "+ iCloud", let Xcode create the container) or the Apple Developer portal — neither of which a coding agent can drive without a display and an interactive login. **Reverted both entitlements files** rather than leave the build broken for whoever runs `script/run` next (verified: build succeeds again post-revert) — every phase must end in a buildable app per §7. Whoever has interactive Xcode access should: add the iCloud capability once via Signing & Capabilities (creating `iCloud.<bundle-id>`), let Xcode write the resulting entitlements, then everything else in this section (the resolver, the migrator, the coordinated I/O, the presenter, the Settings UI) should work against a real container without further code changes — it was all built and tested against the *shape* of this feature, just not the real cloud container. Also fixed in this pass, independent of the entitlements: `Sources/monkey/CLIEnvironment.swift` never actually read `StorageLocationPreference` — it always hardcoded the on-device root, contradicting §5's "the CLI reads whichever root the app's Settings selected." Now resolves via `ConversationsRootResolver.resolve(location:)` with the same on-device fallback `AppEnvironment` uses.

"Sending disabled during migration" is now wired: `ComposerView` takes `isSendingDisabled`, threaded through `ConversationDetailView` from `MonkeyRootView`'s `environment.isMigrating`. Not live-tested (would need a real migration to trigger, which needs the iCloud entitlement above), but it's the same one-`Bool`-prop pattern as the already-verified `onConversationUpdated` wiring.

**Remaining Phase 6 gaps, deliberately deferred rather than half-built:** the iCloud entitlements themselves (see above — needs one interactive Xcode step); per-conversation migration progress UI (there's a global spinner, not one row per folder); `NSMetadataQuery` download-on-demand + placeholder rows; `NSFileVersion` conflict resolution for `conversation.yaml`; and the two-device/iCloud-signed-out test matrix from §7's Phase 6 line — none of that is possible to execute solo, overnight, without a second physical device, a real iCloud account, and interactive Xcode access.

Files app exposure on iOS (`UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace`) is a separate, later question; it would require the local root to be `Documents/` instead of `Application Support/`. Not in v1.

## 4. Core package design

### `FrontmatterDocument`

- Splits a file into the `---`-fenced YAML block and the markdown body; only the split is custom, the YAML itself goes through Yams.
- `parse<T: Decodable>(Data, as: T.Type) throws -> (metadata: T, body: String)` via `YAMLDecoder`.
- `serialize<T: Encodable>(metadata: T, body: String) throws -> Data` via `YAMLEncoder`.
- `conversation.yaml` is plain Yams `Codable` with no fence.
- Tests: round-trip, bodies that contain `---`, empty body, CRLF input, unicode, unknown keys ignored.

### Types

- `ConversationID`, `MessageID` — strongly typed wrappers.
- `Conversation` — `Codable`, decoded/encoded with Yams.
- `Message` — `Codable` frontmatter fields (`id, role, createdAt, status, ...`) plus `body`.
- `MessageRole: user | assistant`.
- `MessageStatus: complete | streaming | cancelled | failed`.
- `TimestampedName` — parse/format the `<timestamp>-<key>` scheme; comparable. Used for both conversation folder names and message file names (`.md` appended).

### `ConversationStore` (actor)

- `listConversations() -> [Conversation]` (sorted by `last_message_at` desc, falling back to `created_at` for empty conversations — `updated_at` is deliberately *not* the sort key, so a rename doesn't jump a conversation to the top)
- `create(title:) -> Conversation`
- `delete(_:)`
- `update(_:)`
- `messageIndex(for:) -> [MessageFileName]` — directory listing, sorted. Cheap; this is what pagination walks.
- `loadMessage(_:) -> Message`
- `loadMessages(_:in range)` — batch
- `write(_ message:in:)` — atomic
- No separate `appendStreaming` method: `write` already handles atomic rewrites regardless of status, and there's no disk-I/O difference between a streaming rewrite and any other write. The throttling ("rewrite at ~250ms cadence") is owned by the caller (`ModelSession`), which knows the real token/chunk cadence — adding an identically-behaved alias on the store would be ceremony, not abstraction.
- Cache: LRU of decoded `Message` values keyed by filename, bounded (e.g. 500 entries or ~N MB of body text). Eviction is the "unload from memory" the spec asks for. Index (filenames) is always resident — it's tiny.
- Optional: use `NSFilePresenter`/`FileCoordinator`? Probably not needed for single-process. Skip unless testing shows a problem.

### `ModelSession` (actor, wrapping `LanguageModelSession` via a `ChatBackend` seam)

- Availability: check `SystemLanguageModel.default.availability` at launch and on foreground. Surface every `.unavailable` reason as a real UI state (device unsupported, Apple Intelligence off, model downloading). Do not silently fail.
- **[verified]**: Apple's own `LanguageModel` protocol is not a lightweight testing seam — conforming to it means implementing a full `LanguageModelExecutor` (the request/response streaming internals real backends use). Faking it directly, as originally planned, is impractical. Implemented instead: a small first-party `ChatBackend` protocol (`identifier`, `availability`, `contextSize`, `tokenCount(for:instructions:)`, `streamResponse(history:instructions:prompt:)`) that `ModelSession` depends on. `SystemChatBackend` implements it for real, driving `SystemLanguageModel`/`LanguageModelSession` directly (never referencing `PrivateCloudComputeLanguageModel`). `FakeChatBackend` (test-only) implements it for Core tests, with no Apple Intelligence dependency.
- One `LanguageModelSession` per open conversation, built from the conversation's `instructions` folded into a rebuilt `Transcript`. Rebuilt on every send in v1 (simpler than caching a long-lived session across instruction changes; revisit if this proves too slow in practice).
- **[verified]** against the macOS 27 SDK: `SystemLanguageModel.contextSize: Int` and `SystemLanguageModel.tokenCount(for: some Collection<Transcript.Entry>) async throws -> Int` both exist (the "26.4+ context-size and token-counting APIs" this plan anticipated). `ModelSession.loadHistoryIfNeeded()` uses them to trim the oldest replayed messages until the remaining transcript fits `contextSize`, rather than a hardcoded count.
- **[verified]**: `GenerationError.exceededContextWindowSize` is deprecated as of 27 in favor of `LanguageModelError.contextSizeExceeded(_:)` (with a richer `ContextSizeExceeded { contextSize, tokenCount, debugDescription }` payload). `ModelSession` catches `LanguageModelError.contextSizeExceeded`: trims the oldest replayed message, retries once, surfaces (message `status: failed`) if it still fails.
- Streaming: `SystemChatBackend.streamResponse` iterates `LanguageModelSession.streamResponse(to:)`'s `ResponseStream<String>` and yields each `Snapshot.content` as the full text so far (not a delta). **[verified]** on real hardware, not just by API naming: this machine has Apple Intelligence enabled, and two live sends through the actual built app ("Say hello in exactly three words." → "Hello, world!"; "What color is the sky? One word answer." → "Blue.") round-tripped correctly end to end — real on-device model, real streamed write, real render, real persistence to disk. Cancellation via `Task` cancellation → mark message `cancelled`, tested (unit test) and confirmed the Stop button appears mid-stream in the live app.
- No tools, no guided generation, no `@Generable` for v1. Plain chat.
- **[verified]** against the macOS 27 SDK: yes, `SystemLanguageModel.Variant` exists (`.core3`, `.coreAdvanced3`, read via `SystemLanguageModel.default.variant`), confirming there _is_ a model tier concept in 27 — but there is no initializer or API to choose one; it's determined by the device. Confirms the plan's default: don't choose, record `SystemLanguageModel.default.variant.displayName` as `model:` (`SystemChatBackend.identifier`).

## 5. Companion CLI (macOS only, bundled)

**Spike finding, corrected in Phase 5** (`spike/1-cli-model-app-group`, throwaway, not merged): a bare sandboxed Mach-O executable hung on launch from Terminal, stuck in dyld's pre-`main()` `_libsecinit_appsandbox` sandbox-init routine. That spike concluded bundling would fix it. **It didn't.** Phase 5 built the real thing — `monkey` embedded at `Monkey.app/Contents/Helpers/monkey`, correct entitlements, correct signing (all verified: `codesign -d --entitlements` shows exactly `app-sandbox` + `application-groups`, no network) — and it hung identically, same `_libsecinit_appsandbox.cold.6` stack, when exec'd directly from this agent's Bash tool shell. The decisive control test: **the main GUI app's own binary** (`Monkey.app/Contents/MacOS/Monkey`), which launches and runs correctly via `open` (proven repeatedly this session — real on-device model conversations, screenshotted), **also hangs when exec'd directly** from the same shell, identical stack trace. A maximally minimal one-line `print()` sandboxed binary with no project code at all hangs the same way.

**Verified outside the agent environment, on the repo owner's own physically-logged-in Mac, via `Terminal.app` — this is now a confirmed platform-level finding, not an agent artifact.** The agent's own shell showed an infinite hang (see above); a real Terminal.app session showed a different, more specific symptom: an immediate `trace trap` (SIGTRAP) crash. Five independent binaries were tested directly in the user's own Terminal to isolate the cause:

| Entitlements                                                                                     | Signing identity         | Result                    |
| ------------------------------------------------------------------------------------------------ | ------------------------ | ------------------------- |
| none                                                                                             | Apple Development        | ✅ runs and exits cleanly |
| `app-sandbox` + `application-groups` + `get-task-allow` (the real, Xcode-built Debug CLI helper) | Apple Development        | ❌ trace trap             |
| `app-sandbox` + `application-groups`, `get-task-allow` manually stripped                         | Apple Development        | ❌ trace trap             |
| `app-sandbox` alone, no app-group                                                                | Apple Development        | ❌ trace trap             |
| `app-sandbox` alone, no app-group                                                                | Developer ID Application | ❌ trace trap             |

This rules out `get-task-allow`, the app-group entitlement, and the signing identity as the cause. The only common factor across every failure is `com.apple.security.app-sandbox=true` on a **standalone (non-`.app`-bundle) executable** launched directly from Terminal — on this specific OS/toolchain pairing (macOS 27.0 build 26A428, Xcode 27.0 build 27A266a). This is a real, reproducible problem with this shipping macOS 27.0 release (not a beta — confirmed by the repo owner), not a defect in Monkey's code, not the app-group entitlement, and not (as an earlier draft of this note incorrectly concluded) an artifact of the coding agent's own shell — the user's ordinary interactive Terminal session hits it too, just with a different symptom (crash vs. hang).

**This is a hard blocker for Phase 5 as currently scoped** (a sandboxed CLI binary you run directly from Terminal). Apple has shipped sandboxed, Terminal-launched CLI tools for years, so this is very likely a regression specific to this release rather than an intentional platform change — but since 27.0 is shipping, not beta, there's no guarantee of a prompt fix via a "next seed." It cannot be worked around from the app's code. Options: (a) file Feedback with Apple including this exact repro table, (b) retest after any macOS 27.x point release, (c) consider an architecture that launches the helper via `launchd`/XPC rather than direct Terminal exec (LaunchServices-mediated launches of sandboxed `.app` bundles work fine, confirmed repeatedly this session) — though that would be a real design change from "run `monkey` directly from Terminal." Do not build out the CLI's command surface as if this works until one of those paths resolves it; the CLI's _logic_ (argument parsing, `ConversationStore`/`ModelSession` usage) can still be built and unit-tested via `swift test`, which needs no sandboxed exec at all.

Ships inside the App Store bundle at `Monkey.app/Contents/Helpers/monkey`. Sandboxed with its own `app-sandbox` entitlement plus the shared app group; no network entitlement. Same rules as the app: no sockets, on-device model only. Built from `Sources/monkey` on `MonkeyCore`; zero UI code. Verified: `codesign -d --entitlements` on the built helper shows exactly `app-sandbox` + `application-groups`, no network.

**Two build-system gotchas found getting this far, both fixed, both worth remembering:**

- The Xcode target for the CLI is named `MonkeyCLI` in `App/project.yml`, not `monkey` — naming it `monkey` (matching the app target `Monkey` differing only in case) corrupted both targets' builds, because Xcode's DerivedData intermediate folders are named after the target and macOS's default APFS volume is case-insensitive: `monkey.build` and `Monkey.build` are the same directory on disk. `PRODUCT_NAME: monkey` still makes the actual output binary lowercase as the CLI spec requires; only the Xcode target identifier had to change.
- `Sources/monkey/main.swift` was renamed to `Monkey.swift`. A file literally named `main.swift` gets implicit top-level-code treatment that conflicts with `@main` when built as a native Xcode target (`error: 'main' attribute cannot be used in a module that contains top-level code`) — SwiftPM's own `swift build` tolerated the old name, but Xcode-native builds of the same target did not. Only `@main`-attributed entry files should avoid the literal name `main.swift`.

App group ID: `group.engineering.xo.Monkey` (reverse-DNS of the repo owner's real `xo.engineering` domain — this is a real shipping app, not a generic template) — hardcoded in both `Monkey.entitlements` and `MonkeyCLI.entitlements` and mirrored as a plain string constant in `MonkeyCore`'s `AppGroupStorage.groupIdentifier` (see below) — a literal in all three because the Swift constant is runtime code that can't see build settings, so the entitlements simply match it (entitlements themselves *can* use `$(…)` substitution; see the correction in §3a). Conventions:

- Conversation references accept a full folder name or any unique prefix (`monkey open 2026-09-15`); ambiguous → list matches and exit 1.
- Message references: `<convo> <message>` where `<message>` is a message file name, a unique prefix, or a negative index (`-1` = last). **[verified]** by direct test: swift-argument-parser 1.8.2 treats a bare dash-prefixed token as an unrecognized option, not a positional value, for a `String?`-typed `@Argument` (its automatic negative-number heuristic only kicks in for numeric-typed arguments, not `message`'s file-name-or-index string). A negative index therefore needs the standard Unix `--` end-of-options separator: `monkey cat <convo> -- -1`. Documented in `cat`'s `--help` text.
- `--json` on any listing/print command for piping. Default output is human-readable.
- stdin: if not a TTY, its contents are appended to the prompt (`cat file.md | monkey do "summarize"`).
- Exit codes: 0 ok, 1 usage/not found, 2 model unavailable (print the availability reason).

Commands (v1 unless marked):

- `monkey ls [--json]` — conversations, latest message first: id, title, message count, updated (`--json` also carries `last_message_at`, null for empty conversations).
- `monkey do <prompt…>` — one-shot. Creates a new conversation on disk (so it shows up in the app), streams the reply to stdout. `--ephemeral` to skip writing.
- `monkey chat [<convo>]` — REPL. No arg = new conversation; with arg = continue that one. `/quit`, `/id` (print the conversation id).
- `monkey cat <convo> [<message>]` — print a message body to stdout (`--raw` includes frontmatter). Without `<message>`, prints the whole conversation as one markdown stream. This is the piping/integration hook.
- `monkey open [<convo>]` — Reveal in Finder: the Conversations root, or one conversation folder.
- `monkey search <query> [--in <convo>]` — case-insensitive substring/regex over message bodies and titles; prints `convo  message  line` hits, `--json` for tooling. Body search is trivial from the CLI; the app UI still only searches titles in v1.
- `monkey see <path> [<prompt…>]` (v2) — image input to the on-device model. **[verify]** iOS/macOS 27 Foundation Models accept image input on-device; WWDC26 coverage says yes. Local paths only — a URL form would require network, which the CLI does not have; if wanted later, `curl … | monkey see -` covers it without changing the entitlements.

Non-goals: no daemon, no HTTP server, no `--model` selection, no cross-device anything (iCloud mode works because the CLI reads whichever root the app's Settings selected, via a shared preference in the group container).

**"Can't create a new conversation" — root cause is a real sandbox/container issue on this machine, isolated but not fixed by me.** Two separate problems layered on top of each other: (1) `ConversationListViewModel.errorMessage` was set on every failure path but never actually displayed anywhere — no `.alert` was wired up, unlike every other view model in the app. Silent failures with zero UI feedback. Fixed by adding the same `.alert` pattern `ConversationDetailView`/`SettingsTabsView` already use. (2) Once the real error was visible, it read `NSCocoaErrorDomain Code=513 "Operation not permitted"` writing into the app-group container — and this reproduced identically under **three different app-group identifiers**, including one (`group.zzznevertested.Monkey`) that had never existed on this machine before that exact test, on a completely fresh `DerivedData` + freshly-deleted container each time. Removing `com.apple.security.files.user-selected.read-write` didn't change it either. Since the failure was identical regardless of the group ID's identity or history, it wasn't a code bug. The first theory — daemons in a bad state from rapid rebuild churn — was **wrong**: a restart changed nothing. **Actual root cause, [verified] the next day:** the app was being signed against Xcode's generic wildcard `Mac Team Provisioning Profile: *`, whose entitlements grant only `application-identifier`/`keychain-access-groups`/`team-identifier` — no `app-sandbox`, no `application-groups`. The `.entitlements` file *requests* the group, but on macOS 15+ the kernel only honors a `group.`-prefixed app group that the provisioning profile actually backs; otherwise every write into the container is `EPERM`, silently (TCC's App Data gate was never even consulted — adding `NSAppDataUsageDescription` was tested and made no difference, so it was removed). Two things were needed to fix it, and both were: (1) one interactive pass through Xcode's Signing & Capabilities tab — select the team, confirm "App Groups" lists `group.engineering.xo.Monkey` for **both** the iOS and macOS rows — which registers the capability on the App ID with Apple (`-allowProvisioningUpdates` never did this headlessly; same limitation as iCloud containers); and (2) **deleting the stale cached wildcard profile** from `~/Library/Developer/Xcode/UserData/Provisioning Profiles/` — even after (1), every `xcodebuild -allowProvisioningUpdates` kept silently reusing the old cached wildcard instead of asking Apple for a new one. Once it was gone, the very next build fetched `Mac Team Provisioning Profile: engineering.xo.Monkey` with `com.apple.security.application-groups = [group.engineering.xo.Monkey]`, and ⌘N created a conversation, a prompt round-tripped through the real on-device model ("pineapple"), and both messages persisted with `status: complete`. Whoever hits `EPERM` on the group container again: check `security cms -D -i Monkey.app/Contents/embedded.provisionprofile` first — if the Name is the wildcard `: *`, delete it from that folder and rebuild. "Show Data Folder in Finder" was the same root cause (Finder now opens the container with `Conversations` selected — verified). The "New Conversation" toolbar button rendering in the `»` overflow was test noise from a forced-narrow window; at the app's natural window size it shows inline. Note that Xcode's UI writes `DEVELOPMENT_TEAM` straight into the tracked `project.pbxproj` when you pick a team there — run `xcodegen generate` afterward to strip it (the downloaded profile persists independently), and don't regenerate *while* someone is still mid-fix in the UI, since it resets the team dropdown to None.

**Correction to an earlier claim in this file:** `.entitlements` files *do* support build-setting substitution — Xcode's own multiplatform templates use `$(AppIdentifierPrefix)…` inside `.entitlements`. The app-group string is hardcoded in three places for a different reason: `AppGroupStorage.groupIdentifier` is runtime Swift and can't see build settings, so the entitlements just match it literally. **The bundled CLI (`MonkeyCLI`) has not been given the same treatment**: it has no bundle identifier, is "Sign to Run Locally" (ad-hoc), and has no provisioning profile at all, so its `application-groups` entitlement isn't profile-backed either — moot for now because the sandboxed helper can't be launched from Terminal anyway (§5 platform bug), but when that clears, it will need a bundle ID and the same App Groups registration, or the app's `AppGroupStorage` fallback to Application Support will be what the CLI actually uses.

**Install Command Line Tool: real sandbox limitation found and worked around, not guessed around.** The original design (§5) called for both install and "uninstall (if installed)." Six consecutive live-tested approaches to support overwriting an existing file at the chosen path, or persisting access for a later uninstall, all failed for concrete, verified reasons: plain `removeItem` on the `NSSavePanel`-granted URL → `EPERM`, even immediately after the panel's own "Replace?" confirmation; `FileManager.replaceItemAt` → `ENOENT` on the original item; a `.withSecurityScope` bookmark of the destination before it exists → "scoped bookmarks can only be created for existing files or directories"; bookmarking the freshly-created symlink → "Could not open() the item"; bookmarking the *containing directory* instead (reasoning: directory-level sandbox grants normally extend to files created within them) → the identical "Could not open() the item," which also reveals that `NSSavePanel`'s grant never covered the containing directory at all — only the exact chosen leaf path, for what appears to be exactly one direct operation. Conclusion, agreed with the user rather than assumed: **`CLIInstaller` only supports fresh installs** (verified reliable, every time, on a path nothing occupies yet). If the chosen destination already exists, it throws a clear, actionable `LocalizedError` ("A file already exists at ‹path›. Remove it manually ... and try installing again.") instead of silently failing or pretending to support a replace it can't perform. No persistent "is it installed" tracking, no Uninstall button — `AdvancedSettingsView` just shows the path from the current session's successful install, forgotten on next launch. Revisit only with a real reason to believe one of the untried angles (e.g. a fresh panel per uninstall attempt, `com.apple.security.files.bookmarks.app-scope`, or Apple DTS input) would actually resolve it — don't re-attempt the same six approaches.
